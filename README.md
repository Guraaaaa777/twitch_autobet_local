# twitch_autobet

Twitch チャンネルを追跡し、チャンネルポイント予想の各選択肢の確率を LLM で推論して、
ケリー基準で賭け金を決めて自動投票するローカルアプリです。

ローカル Web アプリとして動作します (Python + FastAPI バックエンド、ブラウザ UI)。

---

## ⚠️ 先に読んでください

**1. Twitch の非公開 API を使っています**

公式の Helix API には、

- 他人のチャンネルの予想を読む手段
- 自分のチャンネルポイント残高を読む手段
- 視聴者として予想に投票する手段

がいずれも存在しません。そのため本アプリは、Twitch の Web クライアント自身が使っている
非公開 GraphQL API (`gql.twitch.tv`) と PubSub を直接叩いています。

- **Twitch の利用規約に抵触する可能性があります。** アカウント停止のリスクを承知のうえで使ってください。
- スキーマはバージョン管理されておらず、Twitch 側の変更で予告なく壊れます。
  壊れたときは設定画面の **接続テスト** でどのクエリが失敗しているかを確認できます
  (実装は [`app/twitch/gql.py`](app/twitch/gql.py))。

**2. 初期状態はドライランです**

`設定 → 自動投票 → ドライラン` が既定でオンです。この状態では推論・賭け金計算・ログ記録まで
すべて動きますが、実際の投票 API は呼びません。ログで賭け金と根拠を確認してから解除してください。

## セットアップ

### 1. 依存

```bash
python -m venv .venv
```

```bash
.venv/Scripts/python.exe -m pip install -r requirements.txt
```

外部コマンドとして **ffmpeg** (文字起こし用) と **llama-server** (llama.cpp の実行ファイル) が必要です。
ffmpeg は PATH 上にあれば自動で使われます。llama-server と GGUF モデルは設定画面でパスを指定します。

### 2. 起動

```bash
.venv/Scripts/python.exe run.py
```

ブラウザで `http://127.0.0.1:8760/` が開きます。

### 3. 設定

`設定` 画面で最低限これらを入れます。

| 項目 | 内容 |
| --- | --- |
| Twitch OAuth トークン | twitch.tv にログインした状態の Cookie `auth-token` の値 |
| llama-server 実行ファイル | `llama-server.exe` の絶対パス |
| モデル (GGUF) | GGUF ファイルの絶対パス |

`auth-token` はブラウザの DevTools → Application → Cookies → `https://www.twitch.tv` から取得します。
**このトークンはアカウントそのものへのアクセス権を持ちます。** `data/settings.json` に平文で保存されるので、
データディレクトリは他人と共有しないでください。

設定後、`接続テスト` で Twitch と llama.cpp の設定を検証できます。

## 使い方

1. メイン画面でチャンネル名 (表示名ではなく URL の名前) を入力して **登録**
2. 必要なら **固定確率** / **情報付加** を設定
3. **追跡開始**

追跡を開始すると、有効なチャンネルごとに次が走ります。

- ポーリング (既定 5 秒) で予想状況とチャンネルポイント残高を取得
- PubSub で予想の開始/更新をリアルタイム受信
- 音声の文字起こし (直近 30 分ぶんを保持)
- 予想の締め切り 5 秒前に、最新のプール状況を取り直して推論 → 賭け金決定 → 投票

### 固定確率設定

チャンネル単位で「上から順の選択肢の確率」を設定します。有効なあいだ **LLM 推論は行いません**。
値の個数が予想の選択肢数と一致しない予想については、その予想だけ LLM 推論に切り替わります。

### 手動情報付加

投票の概要が事前にわかる場合に入力します。LLM のプロンプトにそのまま含まれます。

## 賭け金の決め方

Twitch の予想は**パリミュチュアル方式**です。負けたプールが、勝った側の賭け金比で分配されます。
つまり自分の賭け金がそのままオッズを下げるので、固定オッズ前提の
`f* = (pb − q) / b` は過剰に賭けます。

選択肢 `i` に既に `T_i` pt、プール全体が `T` pt のとき、`b` pt 賭けた場合の純利益は

```
profit(b) = b × (T − T_i) / (T_i + b)
```

で、純オッズ `B(b) = (T − T_i) / (T_i + b)` は `b` とともに縮みます。そこで期待対数資産

```
g(b) = p × ln(W + profit(b)) + (1 − p) × ln(W − b)
```

を三分探索で直接最大化しています (`g` は `[0, W)` 上で凹)。求めたフルケリー額に
**ケリー係数** (既定 0.25) を掛け、**最大賭け率** (既定 5%) と **最大賭け金** (既定 250,000 pt、
Twitch 側の上限) でクランプします。最終的なエッジが **最低エッジ** (既定 5%) を下回るなら見送ります。

実装は [`app/betting/kelly.py`](app/betting/kelly.py) です。

なお、自分が賭けたあともプールは動きます。`T` と `T_i` は投票時点の値でしかなく、
後から入る資金で実際の配当はずれます。これは決定時点では原理的に知りようがなく、
フルケリーではなく分数ケリーを既定にしている理由のひとつです。

## 設計上の判断

- **ポーリングと PubSub の併用。** 予想ウィンドウは 60 秒のこともあり、ポーリングだけでは
  開始検知が遅れます。PubSub を低遅延の通知に、ポーリングを投票直前の正となる状態取得に使っています。
  PubSub は Twitch のレガシー面なので、繋がらなくてもポーリングだけで完結します。
- **選択肢は番号で渡す。** UUID をそのまま復唱させると小さいローカルモデルは崩すため、
  プロンプトでは 1..N の番号を使い、解析後に outcome id へ戻しています。
- **タイムスタンプは SQLite 形式の UTC 文字列。** `datetime('now', '-30 minutes')` との
  文字列比較が正しく効くようにするためです。ISO-8601 の `T` 区切りだと保持時間の判定が壊れます。
- **文字起こしのチャンクは詰まったら捨てる。** CPU 推論はライブ配信に追いつかないことがあります。
  そのとき必要なのは直近の音声であって、溜まった古い音声ではありません。

## 既知の制約

- 追跡対象チャンネルの増減・Twitch 認証・llama.cpp 設定の変更は、**追跡を再開始するまで反映されません**
  (UI にも警告が出ます)。
- 保有チャンネルポイントは、そのチャンネルでポイントを獲得したことがないと取得できません。
- 文字起こしは CPU では `base` 程度が実用上の上限です。GPU がある環境では
  `設定 → 文字起こし → デバイス` を `cuda` にしてください。
